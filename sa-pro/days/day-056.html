AWS Database Migration Service (DMS) — Homogeneous & Heterogeneous Migration with CDC

DMS + SCT questions are among the most reliable topics on SAP-C02 — expect 3-4 direct or scenario-embedded questions. This lesson covers the full architecture, migration-type decision tree, load strategies, sizing, LOB handling, validation, and the exam's favorite edge cases, plus 15 practice questions.

AWS DMS AWS SCT Change Data Capture (CDC) DMS Serverless Aurora / RDS

1. Overview — Why DMS Matters on the Exam

AWS Database Migration Service (DMS) migrates data from a source database into AWS (RDS, Aurora, Redshift, S3, OpenSearch, Kinesis, DynamoDB, and more) while the source database stays online and continues serving production traffic. That "source stays live" property is the whole point: it's what makes near-zero-downtime cutovers possible, and it's the detail most exam scenarios are testing for when they describe a company that "cannot tolerate extended downtime" during a database migration.

DMS is a data-movement engine. It does not, by itself, create or convert a target schema. Whether you need a companion tool to handle the schema depends entirely on whether the source and target run the same database engine — which is the single most important branching decision in this whole topic.

2. Core Architecture

Replication Instance

The compute engine that actually runs your migration task(s) — an AWS-managed EC2 instance running the DMS engine. Larger instance classes provide more memory (for caching changes/rows in flight) and more CPU (for transformation rules and, in heterogeneous migrations, data-type conversion). Undersized replication instances are the most common real-world DMS performance bottleneck, and a very common exam distractor. Place the replication instance in the same VPC/AZ as the target database to minimize network latency and avoid unnecessary cross-AZ data transfer charges.

Endpoints

Connection definitions for your source and target. DMS supports an extensive source/target catalog: Oracle, SQL Server, PostgreSQL, MySQL/MariaDB, MongoDB, SAP ASE, and on-prem or EC2-hosted databases as sources; RDS, Aurora, Redshift, OpenSearch Service, Kinesis Data Streams, S3, and DynamoDB as targets (and vice versa for many of these).

Replication (Migration) Tasks

A task defines what moves and how: table mappings (include/exclude rules, schema/table selection), transformation rules (rename, filter, or modify data in flight), and the migration type (full load, CDC, or full load + CDC — see below).

3. Homogeneous vs. Heterogeneous Migration — The Core Decision Tree

The exam consistently tests whether you know when SCT is required. The rule is simple:

CharacteristicHomogeneous (same engine family)Heterogeneous (cross-engine)
ExampleOn-prem SQL Server → RDS SQL ServerOracle → Aurora PostgreSQL
Schema conversion needed?No — but schema must be pre-created (native tools like pg_dump/restore, or native backup/restore, are typically faster than DMS for the initial load)Yes — AWS Schema Conversion Tool (SCT) required to convert tables, views, stored procedures, and functions
Secondary objects (indexes, FKs, triggers)Not automatically migrated — must be scripted/migrated separatelySCT attempts conversion; complex procedural code often needs manual rework
Transformation rulesLimitedFull support — column/table renaming, data-type mapping, filtering
Relative cost/complexityLowestModerate to highest

Exam gotcha: a 90-95% automatic SCT conversion rate sounds like the migration is basically done. It isn't — the remaining 5-10% is disproportionately the hardest part (complex stored procedures, triggers, proprietary SQL extensions) and needs manual developer remediation before cutover. Never pick an answer implying a heterogeneous migration is "fully automated."

4. Full Load vs. CDC vs. Full Load + CDC

  • Full Load Only — migrates a point-in-time snapshot of existing data. Simplest option, but the source is effectively frozen (or you accept data drift) for the duration, so it implies real downtime for the cutover.
  • CDC Only — replicates ongoing changes from a defined start point (e.g. a transaction log position), assuming the base data already exists at the target (perhaps loaded natively). Used for ongoing replication or as the second half of a two-step migration.
  • Full Load + CDC — the standard near-zero-downtime pattern: DMS takes a full-load snapshot while simultaneously caching changes that occur during the load, applies the cached changes once the load completes, then keeps streaming CDC until you're ready to cut over. The cutover maintenance window shrinks to seconds to a few minutes — just long enough to stop writes to the source, let final CDC changes apply, and repoint the application.

Exam pattern: any scenario stressing "minimal downtime," "cannot take the database offline," or "near-zero downtime cutover" is pointing you at Full Load + CDC.

5. Replication Instance Sizing & DMS Serverless

Monitor CPUUtilization, FreeableMemory, and SwapUsage on the replication instance. Memory pressure causes the instance to spill to disk, tanking throughput; CPU saturation shows up during heavy transformation rules or high-volume CDC apply. A single task rarely exceeds ~100,000 rows/second — for higher aggregate throughput, parallelize across multiple tasks (e.g. one task per large table, or partitioned table mappings).

DMS Serverless removes manual instance sizing by auto-provisioning and auto-scaling DMS Capacity Units (DCUs) based on workload. Rough starting guidance: under 100GB → 2-4 DCU minimum; 100GB-1TB → 4-8 DCU minimum; over 1TB → 8-16 DCU minimum, scaling to 64+ DCU as needed. This is the right answer whenever a scenario emphasizes unpredictable migration workloads or wanting to avoid capacity planning.

Also monitor CDCLatencySource and CDCLatencyTarget: source-side latency points to slow reads from the source transaction log; target-side latency points to slow apply on the target (often an undersized target instance or missing indexes).

6. Large Object (LOB) Handling

  • Full LOB Mode — migrates complete LOBs of any size, but processes rows sequentially (piece by piece), which is slow.
  • Limited LOB Mode — truncates LOBs above a size threshold you set, enabling parallel processing (fast) — but any LOB larger than the threshold is silently truncated, risking data loss if set too low.
  • Inline LOB Mode — handles LOBs under a set size threshold inline with the row (fast); larger ones are migrated separately in a second pass. This gets you both speed and completeness when most LOBs are small.

Exam tip: if a scenario says "profile the source data first and most LOB columns are under 64KB," the correct configuration is Inline LOB Mode with a 64KB threshold — not Limited LOB Mode (which would truncate/lose the occasional larger object) and not Full LOB Mode (needlessly slow).

7. Validation & Monitoring

Enable DMS data validation to automatically compare row counts and checksums between source and target after (or during, for CDC) migration. For business-critical cutovers, supplement this with application-level queries that exercise real business logic, and consider continuous validation during the CDC phase to catch discrepancies within minutes rather than discovering them post-cutover.

8. Edge Cases & Exam Gotchas (Memorize These)

  • Tables without a primary key — CDC needs a way to identify which row changed. Without a PK (or at least a unique index), DMS falls back to full-table scans per change, which can degrade CDC performance by orders of magnitude. Add a PK/unique index before migrating, or expect this to be the "why is CDC so slow" answer.
  • Sequences / identity columns — values do not auto-synchronize between source and target. After cutover, you must run a post-migration script to reset sequence values above the highest migrated ID, or new inserts will collide.
  • Triggers and computed columns — can fire during migration and cause duplicate writes or constraint violations. Standard practice: disable triggers before migration, re-enable after cutover.
  • Partitioned tables — need explicit configuration in table mappings; mishandling silently skips data or fails in confusing ways.
  • Homogeneous ≠ everything migrates — homogeneous migrations do not automatically bring over secondary objects (indexes, foreign keys, triggers, stored procedures); these need separate handling even when no engine conversion is happening.
  • DMS does not create the target schema — for homogeneous migrations you must pre-create the schema (native tools are typical); for heterogeneous migrations, SCT's schema-conversion output is applied to the target before DMS moves data.

9. DMS vs. SCT vs. MGN vs. DataSync — Don't Mix These Up

ServiceWhat it actually does
AWS DMSMoves data between databases (or database-to-analytics targets), optionally with CDC. Doesn't convert schema.
AWS SCTConverts schema and code (tables, views, stored procedures) for heterogeneous migrations. Doesn't move data — DMS does that part.
AWS MGNRehosts entire servers/applications (continuous block-level replication) to EC2 — not database-specific.
AWS DataSyncTransfers files/objects (NFS, SMB, HDFS) between on-prem storage and AWS storage — not database-aware.

Exam scenarios love disguising "we need to migrate our Oracle database to Aurora PostgreSQL" behind extra detail — the answer is always the SCT (schema) + DMS (data, with CDC for low downtime) pair, never MGN or DataSync.

10. Hands-on Lab (45 min)

Architect a zero-downtime database migration from on-prem MySQL to Aurora MySQL:

  1. Provision a DMS replication instance sized for the source data volume (or use DMS Serverless) inside the target VPC.
  2. Since this is homogeneous (MySQL → Aurora MySQL), pre-create the target schema (mysqldump --no-data, or native export/import) — no SCT needed.
  3. Create source and target endpoints, then a migration task set to Full Load + CDC.
  4. Enable data validation on the task.
  5. Start the task; monitor CDCLatencySource/CDCLatencyTarget until CDC lag is near-zero.
  6. Plan the cutover window: stop writes to source → wait for final CDC apply → repoint application connection string to Aurora → resume writes.
  7. Post-cutover: reset any auto-increment columns above their migrated max value, and re-enable any triggers disabled pre-migration.

11. Scenario Question Drills — 15 Questions

Q1. A company is migrating an on-premises Oracle database to Amazon Aurora PostgreSQL. Stored procedures make heavy use of Oracle-specific PL/SQL extensions. What is the correct migration approach?

A. Use AWS DMS alone with transformation rules
B. Use AWS SCT to convert the schema and code first, remediate any objects SCT can't auto-convert, then use AWS DMS (Full Load + CDC) to migrate the data
C. Use AWS MGN to rehost the database server as-is
D. Manually export and import the data using SQL scripts only
Correct answer: B. This is a heterogeneous migration (Oracle to PostgreSQL), so SCT must convert schema/code first; DMS handles the data with CDC for minimal downtime. Expect PL/SQL-heavy stored procedures to require manual remediation after SCT's automated pass.

Q2. A migration task shows healthy full-load throughput, but once CDC begins, apply latency on the target climbs steadily. The source table has no primary key. What is the most likely cause?

A. The replication instance is in the wrong region
B. Without a primary key or unique index, DMS must full-scan the target table to locate each changed row during CDC apply
C. CDC does not support MySQL as a source
D. The target endpoint SSL certificate expired
Correct answer: B. Missing primary keys/unique indexes force DMS into full-table scans to apply each CDC change, degrading performance by orders of magnitude as the table grows.

Q3. Which migration type minimizes the cutover downtime window to seconds or a few minutes?

A. Full Load only
B. CDC only, with no prior full load
C. Full Load + CDC
D. Schema conversion only
Correct answer: C. Full Load + CDC captures changes during the initial snapshot and continues streaming them, so the actual cutover is just stopping writes briefly and letting the last CDC changes apply.

Q4. After a successful DMS migration and cutover, new rows inserted into the target Aurora MySQL database are failing with duplicate key errors on the auto-increment primary key. What was missed?

A. Data validation was never enabled
B. The target's AUTO_INCREMENT counter was never reset above the highest migrated ID
C. The replication instance was undersized
D. LOB mode was set incorrectly
Correct answer: B. Sequence/identity/auto-increment values don't auto-synchronize with DMS; a post-migration step must advance the counter past the highest migrated value.

Q5. A profiling step shows 99% of LOB columns in the source table are under 64KB, with a rare few reaching 10MB. Which LOB setting is most efficient without losing data?

A. Full LOB mode
B. Limited LOB mode with a 64KB max size
C. Inline LOB mode with a 64KB inline threshold
D. Disable LOB migration entirely
Correct answer: C. Inline mode migrates small LOBs fast (inline with the row) while still fully migrating the rare large ones in a second pass — Limited mode would truncate/lose the 10MB objects.

Q6. A company migrating on-prem SQL Server to RDS SQL Server (same engine) is surprised that after the DMS migration, none of their indexes, foreign keys, or stored procedures exist on the target. Why?

A. DMS failed silently
B. Homogeneous migrations don't automatically migrate secondary schema objects — only data
C. SCT should have been used instead
D. CDC mode must be enabled to migrate indexes
Correct answer: B. Even in homogeneous migrations, DMS moves data, not the full schema/secondary objects. Native tools (backup/restore, scripted DDL) should migrate indexes, FKs, triggers, and procedures.

Q7. Which CloudWatch metrics are most useful for determining whether CDC lag originates from reading the source or applying to the target?

A. CPUUtilization and FreeableMemory only
B. CDCLatencySource and CDCLatencyTarget
C. NetworkIn and NetworkOut
D. FreeStorageSpace
Correct answer: B. CDCLatencySource isolates read-side delay from the source transaction log; CDCLatencyTarget isolates apply-side delay on the target — together they pinpoint where the bottleneck is.

Q8. A migration workload's data volume is highly unpredictable week to week, and the team wants to avoid manually sizing and re-sizing a replication instance. What should they use?

A. A dms.r6i.24xlarge provisioned instance, sized for peak
B. DMS Serverless, which auto-scales DMS Capacity Units to match workload
C. Multiple small provisioned instances running in parallel
D. AWS DataSync instead of DMS
Correct answer: B. DMS Serverless is designed exactly for unpredictable/variable workloads, removing manual capacity planning by auto-scaling DCUs.

Q9. During a heterogeneous migration, SCT reports a 93% automatic schema conversion rate. What is the correct interpretation?

A. The migration is essentially finished; proceed straight to cutover
B. 7% of objects (often the most complex, e.g. certain stored procedures) still require manual remediation before the migration is production-ready
C. 7% of the data will be permanently lost
D. SCT should be re-run with different settings until it reaches 100%
Correct answer: B. The unconverted percentage is usually the hardest, most complex objects and needs manual developer work — a high conversion percentage does not mean the migration is complete.

Q10. A single DMS task is capped at roughly how many rows/second of throughput, meaning very high-volume migrations should be split across multiple tasks?

A. ~1,000 rows/second
B. ~100,000 rows/second
C. ~10 million rows/second
D. There is no practical per-task limit
Correct answer: B. A single task rarely exceeds ~100,000 rows/second; higher aggregate throughput requires parallelizing across multiple tasks (e.g. per large table or partition).

Q11. Which tool should be used to move a large on-prem NFS file share into Amazon EFS as part of a broader migration project that also includes a DMS database migration?

A. AWS DMS, configured for file targets
B. AWS DataSync
C. AWS SCT
D. AWS MGN
Correct answer: B. DataSync is the file/object transfer tool (NFS/SMB/HDFS to S3/EFS/FSx); DMS is database-specific and doesn't move general file shares.

Q12. A table has triggers that fire on INSERT to enforce business logic. During a Full Load + CDC migration, duplicate side effects are observed on the target. What is the standard remediation?

A. Switch to CDC-only mode
B. Disable the triggers before migration and re-enable them after cutover
C. Increase the replication instance size
D. Enable Limited LOB mode
Correct answer: B. Triggers fire during migration unless explicitly disabled, causing duplicate side effects or constraint violations as DMS writes rows; disable before migration, re-enable post-cutover.

Q13. Which combination correctly matches tool to purpose for a heterogeneous database migration?

A. DMS converts schema; SCT moves data
B. SCT converts schema and code; DMS moves the data
C. MGN converts schema; DataSync moves data
D. A single DMS task handles both automatically with no other tools
Correct answer: B. SCT = schema/code conversion. DMS = data movement (with optional CDC). This pairing is the single most tested DMS fact on the exam.

Q14. A company wants ongoing, continuous replication from an on-prem Oracle database into an S3 data lake in Parquet format for analytics, with no plan to ever cut over the source. What DMS configuration fits?

A. Full Load only, re-run daily
B. Full Load + CDC targeting S3, used as an ongoing CDC pipeline rather than a one-time cutover
C. AWS SCT alone
D. AWS Snowball for a one-time export
Correct answer: B. DMS to S3 is a common CDC-pipeline pattern for streaming database changes into a data lake continuously — the source database is never cut over, it's a permanent replication feed.

Q15. Where should the DMS replication instance be placed relative to the target database to minimize latency and cross-AZ data transfer cost?

A. In a separate region from both source and target
B. In the same VPC/AZ as the target database
C. In the same VPC/AZ as the source database, regardless of target location
D. Placement doesn't affect performance or cost
Correct answer: B. Co-locating the replication instance with the target minimizes apply-side latency and avoids unnecessary cross-AZ data transfer charges on the (typically larger) volume of data being written.
