Case study

An iPhone app compiled on a laptop that can’t legally make one.

openGym is a self-hosted gym tracker by Duarte Santos. Its iOS app is a Capacitor project, and Capacitor cannot be built on Linux — it ships CocoaPods podspecs, no Swift Package Manager manifest, a storyboard and an asset catalog. This is how that app got onto a phone anyway, from a Fedora machine that has never had a Mac on it.

None of the product is mine. The tracker, the training logic, the exercise catalogue and the interface are all openGym's, under the AGPL. What follows is the work of getting that project to build somewhere its authors never intended — and the two pieces of standing on other people's work that made it possible: xtool, which replaces Xcode on Linux, and whoever wrote the 6,554-file catalogue behind those exercise demos.

Why it did not work, and what was true instead

Most of the work was finding out which of the obstacles were real. Three of them were believed to be impossible and turned out to be a different problem entirely.

×

Capacitor cannot be built on Linux

True, and final. @capacitor/ios ships only .podspec files, so SwiftPM cannot consume it; xtool builds SwiftPM only, and has no actool or ibtool for the storyboard and icon catalog. The workaround was to stop using it: openGym's Capacitor imports are all dynamic and gated behind MOBILE, so they never reach a web bundle. Seven modules were reimplemented in JavaScript against a single WebKit message handler, and openGym's own application code is unmodified.

✓

The Xcode download was truncated

92 bytes short — in the trailing metadata, not the payload. The file's own table of contents declares the length it should be, so the shortfall was measurable rather than a guess. xtool installed it without complaint and produced iPhoneOS27.0.sdk.

✓

Apple's Xcode archive still describes its own contents

The format is not what the references say. The table of contents sits at offset 28 rather than at the end, which is why libarchive reports a perfectly good file as corrupt, and the inner header does not parse as documented. Ignoring the header and chaining the compression streams through the decompressor read all of it.

×

Screenshots off the phone are not available

Not from here. The usual tool needs a Developer Disk Image mounted on the device, and Xcode 27 does not ship one — Apple fetches them when a Mac attaches a phone. Decompressing the whole archive settled it rather than assuming.

The numbers that decided it

Each of these came out of measuring something, and each changed what got built.

9.06 GB decompressed out of a 1.9 GB Xcode archive, to search it. Zero Disk Images found.
1.35:1 the gold accent on white, measured. Now 4.51:1. Four of eight accents failed; all eight were solved for.
13,109 copyrighted exercise images ruled out of the public repository, and kept out of the app bundle git too.
139 notification lines across five registers, from 117 on the first pass once the copy started colliding.

What is on the phone

A full native shell: the app's own state mirrored to durable storage, scheduled workout reminders and streak milestones, a Keychain for the two secrets it holds, the share sheet for backups, and the print sheet for the weekly plan. Exercise demos are 6,554 images of a catalogue that never leaves the device.

The live camera QR scanner is not implemented. Photo import of a check-in code works, because the decoder the browser build already ships turned out to be pure JavaScript. Rebuilding ML Kit's full-screen camera UI was not worth the risk to a working app.

How a build runs

Two commands, on Linux, with no Xcode, no signing certificate held by hand and no Mac in the loop.

  1. Swift 6.4.1 and xtool 1.22.2The cross-platform Xcode replacement. Swift is not in Fedora's repositories; it comes from swift.org, and the closest published build is Fedora 41.
  2. A Darwin SDK from Xcode 27Built from the archive, slim, in about twelve minutes.
  3. The web bundleA phone-flavour Vite build with the native shims aliased in, plus 6,554 exercise stills.
  4. The appA SwiftPM shell that xtool turns into an .app, signed against a free Apple ID and installed over USB.

$ cd ios-shell && xtool dev run

Credits

This page describes other people's software. All of it is worth using, and the first entry is the one that matters.

openGym — Duarte Santos

The self-hosted gym and bodyweight tracker this app is. Every workout, routine, set, progression rule, chart and screen is theirs, under the AGPL-3.0-or-later; the training logic is a set of pure functions with unit tests beside them, and it is the reason there is anything here to package. Also a 6,554-exercise catalogue, 19 languages, and roughly 1,800 commits maintained to a release every two weeks.

If you want the original, it is the better product and it runs on Linux, Docker, a NAS or a Raspberry Pi in about four minutes: docker compose up. This page is only about getting their code onto an iPhone, which is a narrower thing.

xtool — the xtool contributors

The cross-platform replacement for Xcode, MIT licensed. It parses Apple's Xcode archive, builds a Darwin Swift SDK from it, and links a SwiftPM package into a signed .app on Linux. Nothing on this page would exist without it — every step that was not a dead end was xtool doing something the documentation did not promise.

Release 1.20.1's notes mention Xcode 27 linking specifically, which is the version this build ended up using.

Everyone else this leans on

  • Gym visual — Aliaksandr Makatserchyk, for the exercise illustrations and animations. Licensed to openGym, not redistributable, which is the single hardest constraint on publishing any of this.
  • Melih Colpan — MuscleMap, MIT, for the body-map geometry behind the muscle heatmaps.
  • Swift, LLVM, swift-corelibs — Apache 2.0 with LLVM exceptions. The toolchain.
  • jsQR — cozmo, Apache 2.0, the fallback decoder for QR check-in codes.
  • The Fedora and libimobiledevice communities — for making an iPhone talk to Linux at all.
